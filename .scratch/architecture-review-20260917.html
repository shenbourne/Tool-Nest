Problem:

Both router/index.ts and tool.store.ts independently call import.meta.glob('/tools/*/index.ts'), loading every tool module twice. The router extracts routes; the store extracts a ref. Two modules with the same responsibility, no single source of truth.

Solution:

Extract a tool-registry.ts module that owns the glob scan and exports allTools. Router and store import from it. One seam, one place to change the scanning strategy.

Wins:

  • Locality: glob logic lives in one module
  • Leverage: change scanning once, both consumers update
  • Deletion test: removing either current scanner breaks half the app

Unify the scattered preference identity

Strong ports & adapters
apps/web/src/stores/theme.store.ts
apps/web/src/stores/preferences.store.ts
apps/web/src/composables/useLocale.ts
apps/web/src/main.ts
apps/web/src/pages/SettingsPage.vue

Before — 3 modules, overlapping state

theme.store — mode, isDark, localStorage
preferences.store — theme, language, favorites, recentTools, server sync
useLocale — locale, localStorage
main.ts — reads locale from localStorage directly
SettingsPage — writes to both locale stores + preferences

Theme stored in 2 places. Locale logic in 3. No sync between theme.store and preferences.store.

After — one preference module, adapter for persistence

preferences module (deep)
interface: theme, language, favorites, recentTools, settings
implementation: localStorage adapter, server sync adapter, system-preference watcher
theme.store → deleted
useLocale → deleted
main.ts → reads from preferences module

Problem:

Theme lives in theme.store AND preferences.store. Locale logic is split across useLocale, main.ts, and preferences.store. Changing "how preferences work" means editing 3+ modules that leak into each other.

Solution:

Merge theme.store and useLocale into preferences.store. The deepened module owns all user preference state with localStorage and server-sync as internal adapters — callers see one interface.

Wins:

  • Locality: all preference state in one module
  • Leverage: one interface for "what does the user prefer"
  • Delete 2 shallow stores; one deep module remains
  • SettingsPage stops coordinating 3 writers

Every Vue component re-fetches its own tool definition from the store, wraps itself in ToolLayout, and repeats identical boilerplate.

After — deep tool module with thin wrappers

defineTool (deep)
interface: defineTool({ name, logic, ui? })
implementation: auto-wraps in ToolLayout, auto-registers route, auto-fetches tool def. Author writes logic + optional UI.

Problem:

Every tool Vue component repeats: import ToolLayout, look up own definition from store by hardcoded path, pass it as prop. The defineTool interface is shallow — it provides metadata but no structural leverage over the 115 implementations.

Solution:

Deepen defineTool to own the ToolLayout wrapping and route registration. Tool authors provide logic + optional custom UI template. The seam absorbs the boilerplate that currently repeats across 115 files.

Wins:

  • Leverage: one seam governs wrapping for all 115 tools
  • Locality: tool self-reference eliminated
  • Adding a tool becomes a 1-file change for simple tools
  • Deletion test: removing defineTool collapses the entire tool system

After — typed repository interface

flowchart LR
  R["routes/user.ts"] -->|"getUserPrefs()"| REPO["UserPrefsRepo"]
  R2["routes/reports.ts"] -->|"create()"| REPO2["ReportRepo"]
  REPO --> Y["yaml-storage (internal)"]
  REPO2 --> Y
  style REPO fill:#1e293b,stroke:#0f172a,color:#fff
  style REPO2 fill:#1e293b,stroke:#0f172a,color:#fff
  style Y fill:#e0f2fe,stroke:#0284c7

YAML is an implementation detail. Repos are testable with in-memory adapters.

Problem:

yaml-storage.ts exposes generic readYaml<T>/writeYaml<T>, forcing callers to cast through unknown. store.ts mixes domain logic (migration, validation) with serialization. The YAML format leaks into route handlers.

Solution:

Introduce UserPrefsRepository and ReportRepository interfaces. YAML storage becomes a private adapter behind the seam. Two adapters (YAML + in-memory) justify the seam and make the repos testable without touching the filesystem.

Wins:

  • Locality: migration logic stays inside the repo
  • Two adapters = real seam, testable without fs
  • Interface shrinks; implementation absorbs casting
  • Routes stop knowing YAML exists

Eliminate the duplicate sanitizeHtml seam

Speculative in-process
packages/shared/src/validation.ts (line 19-27)
apps/server/src/middleware/security.ts (line 39-46)

Before — same logic, two copies

// packages/shared/validation.ts
export function sanitizeHtml(input: string) { ... }
// apps/server/middleware/security.ts
export function sanitizeHtml(input: string) { ... }

After — one source, re-exported

// packages/shared/validation.ts
export function sanitizeHtml(input: string) { ... }
// apps/server/middleware/security.ts
export { sanitizeHtml } from '@toolnest/shared';

Problem:

Identical sanitizeHtml in shared package and server middleware. A security fix in one location will not reach the other — the two copies can drift silently.

Solution:

Keep the implementation in @toolnest/shared. Server middleware re-exports it. One module owns the sanitization logic.

Wins:

  • Locality: security logic has one home
  • Fix once, both call sites patched
  • Shared package earns its existence

Deepen server config with validation at the seam

Speculative in-process
apps/server/src/config.ts

Before — shallow passthrough

// config.ts — 10 lines
port: parseInt(process.env.PORT || '3001', 10),
corsOrigin: process.env.CORS_ORIGIN || '...',
// No validation. NaN, empty strings,
// invalid URLs all silently pass.

After — validated at the seam

interface: ServerConfig (typed, validated)
implementation: reads env, validates types,
fails fast at startup with clear errors.
Port range check, URL format check,
dataDir existence check on init.

Problem:

config.ts is a shallow passthrough — interface (10 fields) nearly matches implementation (10 parseInt calls). No validation means misconfiguration surfaces as runtime failures far from the source.

Solution:

Add startup validation: port range, URL format, dataDir existence. Fail fast with actionable errors. The config module becomes deep — small interface, substantial implementation (validation logic hidden behind it).

Wins:

  • Locality: config errors surface at startup, not in production
  • Interface stays the same; implementation deepens
  • Deletion test: removing config module = no valid server start

Top recommendation

Unify the scattered preference identity

Three modules (theme.store, preferences.store, useLocale) compete to manage overlapping user state. Theme is stored twice. Locale logic is split three ways. SettingsPage coordinates all of them. Merging into one deep preferences module with localStorage and server-sync as internal adapters gives the codebase a single seam for "what does the user prefer" — the highest-leverage deepening available, touching the most call sites and eliminating the most friction.
