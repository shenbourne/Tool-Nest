## Notes for the next agent

### Repository mechanics

- Do not trust a green `pnpm lint`; it fails on a pre-existing baseline. Use per-file differential lint (`eslint --stdin --stdin-filename` against `git show HEAD:<path>`) for changed files.
- The `.qoder/hooks/commit-lint.mjs` hook validates **every** `-m` argument as a commit subject, so multi-line commit bodies (`-m subject -m body` or heredoc) are rejected. Use a single-line Conventional Commit subject; put detail in the phase docs.
- `pnpm build` and the dev server regenerate `apps/web/src/components.d.ts` (unplugin-vue-components). This file often shows as modified with an **empty** `git diff` — it is a CRLF artefact, not a change; do not stage it.
- `vue-tsc` and `vitest` do not catch malformed SFC structure; only `vite build` does.
- `apps/web/vitest.config.ts` runs in `environment: 'node'` and includes only `src/**/*.test.ts`, so logic inside `.vue` files is untestable. Pure helpers belong in a `.ts` module (`src/utils/*.test.ts` next to `src/utils/*.ts`, or a per-tool `*.service.ts`).

### Media-tool domain rules established in phases 02–03

- A speed control's option value is the **playback-speed multiplier**. Video: `setpts=PTS/<speed>`; audio: `atempo=<speed>` (chained, because `atempo` accepts only `[0.5, 100]`); GIF: `[0:v]setpts=PTS/<speed>,fps=10[v]`. Build these through `apps/web/src/utils/ffmpeg-speed.ts` rather than inline — an inverted `setpts` still produces a valid, playable file, so the mistake is invisible without a duration check.
- `@ffmpeg/ffmpeg` must stay out of Vite's `optimizeDeps`; pre-bundling rewrites its worker URL to a non-existent `node_modules/.vite/deps/worker.js` and `ffmpeg.load()` then never settles.
- `unpkg.com` is unreachable from this machine's browser (~35 s then `ERR_CONNECTION_CLOSED`); `cdn.jsdelivr.net` works, and leads the fallback list.
- The app's `ffmpeg-core` 0.12.6 (FFmpeg **5.1.4**) and local `ffmpeg` **9.0.2** are not interchangeable. Phase 03 recorded this as "the app drops the trailing image's `duration` while the CLI honours it"; phase 04 measured it and that attribution was **wrong** — the demuxer reads the list correctly (`Duration: 00:00:01.50`, 3 frames decoded). The `images-to-gif` frame loss was in the `fps` filter, which ends the stream at the **terminal frame's own timestamp plus its default 1/25 s frame duration** rather than at the container duration, so the frame on that boundary (the last image) was dropped. Verify behaviour that depends on the core version against the core, not the CLI.
- To reproduce core behaviour headlessly, run the same core artifact the app downloads from the CDN in Node: `.scratch/frame-loss-evidence/run-core.mjs` (stages files into MEMFS, logs everything, copies outputs back) plus `verify-cross-version.mjs`, which imports the real `src/utils/image-slideshow.ts` via `node --experimental-strip-types` and compares the core with the CLI. This is much faster than browser automation for anything the CLI cannot reproduce.
- `git fetch origin` failed twice at the start of phase 04 with `TLS connect error: … unexpected eof while reading` (also with `http.sslVerify=false`), and then **succeeded** on the post-development attempt with an empty tree diff against `master`. So that failure is transient network interception on this machine, not a broken remote — retry before recording it as a blocker. The same interception also breaks `curl` (untrusted root) and Node's `fetch` (`SELF_SIGNED_CERT_IN_CHAIN`); `curl -k` does fetch CDN assets, and the browser reaches `cdn.jsdelivr.net` normally.
- A GIF built from a single image cannot store a hold: FFmpeg's `fps`/GIF pipeline derives each delay from the delta to the next frame, and 5.1.4's `gif` encoder has no `delay` option (`ffmpeg -h encoder=gif`). Every input shape yields the encoder's 0.1 s default. It is invisible (a one-frame GIF never advances), so do not chase it.

### Browser verification recipe (Chrome DevTools MCP)

- `upload_file` rejects every path under this workspace, so generate the fixture with the local `ffmpeg`, serve it, and inject it in-page: `fetch('/@fs/D:/…/fixture.mp4')` on the dev server (or cross-origin from the dev server when testing a `vite preview` build, which sends permissive CORS), then build a `File` and assign it to the real `<input type="file">` through a `DataTransfer` plus a `change` event.
- To read a tool's result, walk up from `.n-card` via `el.__vueParentComponent` and read `setupState.resultData`. **This only works in dev builds** — production builds have no `__vueParentComponent`. In a production build, install a `URL.createObjectURL` wrapper and click the download button instead (the page's main world is shared with `evaluate_script`, so the wrapper does catch the blob).
- Measure media with real decoders: `HTMLVideoElement.duration` for video, `ImageDecoder` (`await dec.tracks.ready`, then sum `image.duration`) for GIF frame count and total duration. `image.duration` is in microseconds; for per-frame colour checks draw each frame onto an `OffscreenCanvas` and read the centre pixel.
- On a dev server you can `await import('/src/composables/useFFmpeg.ts')` inside `evaluate_script` and get the **same** module instance the component uses, so `runFFmpegTask`/`exec` can run a deliberately old command shape against the already-loaded core. That is how phase 04 captured the pre-fix behaviour in the same browser session as the post-fix behaviour instead of needing a code revert.
- The web dev server listens on `:3000` (`apps/web/vite.config.ts`); phase 03's notes say `:3411`, which was that session's fallback port.
- Keep a single `evaluate_script` call under roughly 20 s of work; long polling loops make the MCP call fail with "tool invocation did not complete".
